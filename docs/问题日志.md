- **API响应**：`curl http://localhost:8000/api/videos` 返回000（超时）

### 问题分析
1. **核心问题**：ffmpeg转码进程（视频ID 44的`generate_playback_video`转码）耗尽CPU资源
2. **视频信息**：474MB视频文件，时长24分钟，分辨率720x960，非正方形像素（406:405）

### 根本原因
1. **软件编码效率低下**：使用`libx264`纯软件编码，未利用树莓派GPU硬件加速能力
2. **多线程资源竞争**：ffmpeg默认使用多线程并行编码，即使低优先级（nice 19）仍会占满CPU核心
3. **长视频转码耗时**：474MB视频转码需要大量计算资源，预计耗时超过30分钟
4. **同步处理阻塞**：转码在API请求处理线程中同步执行，阻塞服务响应
5. **缺少资源限制**：未限制ffmpeg线程数、运行时间或CPU使用率

## 2026-03-12 00:05 优化方案实施记录

### 实施详情
短期优化方案（1-2小时内可实施）已全部完成：

1. **硬件加速编码**：
   - 修改 `backend/utils/ffmpeg.py` 中的 `generate_playback_video` 函数
   - 优先使用 `h264_v4l2m2m`（树莓派Video4Linux2硬件编码器）
   - 硬件编码失败时自动回退到 `libx264` 软件编码器

2. **限制编码线程**：
   - 添加 `threads=2` 参数限制CPU核心使用
   - 避免多线程并行编码占满CPU核心

3. **优化转码参数**：
   - CRF从22提高至25（降低质量换取速度）
   - 预设从 `veryfast` 改为 `superfast`（进一步加快编码速度）
   - 添加 `bf=0` 禁用B帧，减少计算复杂度

4. **添加进程超时**：
   - 使用 `subprocess.run(timeout=1800)` 替代 `ffmpeg.run()`
   - 为ffmpeg设置最大运行时间30分钟
   - 缩略图生成也添加30秒超时

5. **中文文件名兼容性**：
   - 修复 `routers/videos.py` 中下载API的中文文件名编码问题
