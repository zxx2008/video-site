# 修改日志

## 2026-03-12 00:05:00 CST

### 问题原因
基于《问题日志.md》中记录的系统性能问题，ffmpeg转码进程（视频ID 44）占用318% CPU导致系统负载飙升至10.57，API请求超时。根本原因是纯软件编码效率低下，缺少硬件加速和资源限制。

### 修改方案
实施短期优化方案，全面改进视频转码性能：

1. **硬件加速编码**：优先使用树莓派Video4Linux2硬件编码器 `h264_v4l2m2m`，失败时回退到 `libx264`
2. **资源限制**：添加 `threads=2` 限制CPU核心使用，防止占满所有核心
3. **转码参数优化**：CRF从22提高至25，预设从`veryfast`改为`superfast`，禁用B帧（`bf=0`）
4. **进程超时控制**：使用 `subprocess.run(timeout=1800)` 替代 `ffmpeg.run()`，设置30分钟超时
5. **中文文件名兼容性**：修复下载API的中文文件名编码问题

### 修改内容
```diff

-            vcodec="libx264",
```

### 受影响文件
- `backend/utils/ffmpeg.py`
- `backend/routers/videos.py`

### 实施效果
1. **转码性能提升**：13MB测试视频转码耗时17.39秒，成功使用硬件编码器
2. **资源控制有效**：ffmpeg进程限制为2线程，CPU占用可控
3. **超时机制可靠**：支持30分钟进程超时，防止无限转码
4. **兼容性改善**：下载API支持中文文件名，符合RFC 5987标准
5. **系统稳定性**：所有API功能通过回归测试，响应时间<10ms
6. **安全阈值保障**：转码期间系统负载预计保持在<5.0

## 2026-03-11 23:19:41 CST

### 问题原因
用户上传视频（ID: 44）后，网站主页无响应。经检查发现：
- 上传的视频存在非正方形像素（406:405），触发了 `generate_playback_video` 转码流程
- ffmpeg 转码进程占用了 **281% CPU**，导致系统负载飙升至 8.81
- 高 CPU 占用阻塞了 FastAPI 服务响应，表现为网站访问超时

### 修改方案
在 `backend/utils/ffmpeg.py` 中为所有 ffmpeg 调用添加 `nice -n 19` 参数：
1. `generate_playback_video` 函数（第191行）
2. `generate_thumbnail` 函数（第212行）

修改后 ffmpeg 进程将以最低优先级（19）运行，避免转码任务拖垮系统性能。

### 修改内容
```diff
-            .run(quiet=True)
+            .run(quiet=True, cmd=['nice', '-n', '19', 'ffmpeg'])
```

### 受影响文件
- `backend/utils/ffmpeg.py`

### 实施效果
1. 终止了高 CPU 占用的 ffmpeg 进程（PID 91281）
2. 重启 videohub 服务后系统负载从 8.81 降至 2.12
3. 网站 API 响应恢复正常（HTTP 200）
4. 视频 44 的转码将在下次播放时以低优先级继续
